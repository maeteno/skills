# ROOT

本文件定义根目录下的组织结构、AI Agent 访问边界和协作约定，适用于所有下级目录。
本文件所在目录是其下级目录树的唯一根目录（以下简称“根目录”）。执行任务时不得从本目录向上查找其他 `AGENTS.md`；运行环境已经加载的系统、用户及其他上层规则不因本约定失效。

## 核心约定

1. **根目录边界**：Agent 主动执行的所有文件操作，包括列目录、搜索、读取、创建、修改、移动、删除及生成文件，均限于本根目录内。不得通过绝对路径、`..`、符号链接或工具间接访问根目录外的文件；工具链和运行时自动管理文件的例外仅按第 7 条处理，工作区 `knowledge` 软链接按 `KNOWLEDGE` 规则处理。
2. **工作区隔离**：不同 `WORKSPACE` 之间相互隔离，隔离同时适用于读取、搜索和写入。不得为了当前工作区的任务访问另一个工作区，也不得使用跨工作区索引绕过隔离。
3. **工作区内可查询**：确定当前工作区后，可以查询该工作区内与任务相关的项目、代码、索引、变更记录和知识库；`KNOWLEDGE` 按其独立规则处理。可查询不代表可以任意修改。
4. **项目内可协作**：同一个 `PROJECT` 下的多个代码仓库可以根据任务需要共同读取和修改，例如同一项目的前端与后端。该权限不自动扩展到同一工作区的其他项目。
5. **按任务修改**：写入须服务于当前任务。同一工作区内涉及其他项目的修改，须先明确其属于用户要求的任务范围；不得顺带修改无关资源。
6. **根目录任务**：维护本文件或根目录结构时，只访问根目录层面的必要文件和目录信息，不默认进入各工作区。目标工作区无法确定时，应先询问，不得通过遍历所有工作区猜测。
7. **任务产物同样受限**：Agent 主动创建、复制或导出的临时文件、日志、导出文件、索引及其他任务产物须位于根目录内，并归属当前工作区或当前根目录任务。执行仓库既有构建、测试命令产生的输出，工具链自动管理的缓存，以及 Agent 运行时的会话文件，遵循其既定位置，不视为任务产物；不得借这些位置存放、读取或传递任务内容以绕过访问边界。
8. **非技术隔离**：本文件仅约束 Agent 行为，不构成安全沙箱；需要强制隔离时，应另行配置文件系统权限、容器或工具权限策略。

## 类型标识与规则继承

1. 承担下述组织职责的目录应包含 `AGENTS.md`，第一行使用一级标题声明类型，例如 `# WORKSPACE`；代码仓库的 `AGENTS.md` 可按需设置，存在时使用 `# REPO`。普通源码、资源等子目录不要求逐层创建此文件。
2. 合法类型为：`ROOT`、`WORKSPACE`、`PROJECT`、`REPOS`、`REPO`、`CHANGE`、`WIKI`、`KNOWLEDGE`。`WORKSPACES` 仅表示多个工作区，不作为类型标识。
3. 类型表示职责，不要求目录名与类型名相同。现有目录以其 `AGENTS.md` 声明为准，不得仅为符合示例而自动移动或重命名。
4. 执行任务前，依次读取从根目录到目标目录路径上已有的 `AGENTS.md`。进入新的子目录范围前，先检查其适用规则；不得读取其他工作区的规则文件。
5. 下级约定可以补充工作方式或收紧权限，不能放宽本文件的根目录边界、工作区隔离和 `KNOWLEDGE` 独立性。约定冲突且无法判断时，暂停受影响的操作并询问用户。
6. 缺少下级 `AGENTS.md` 时，继承最近的上级约定；不得据此推断额外权限，也不自动创建文件。

## 目录结构

以下为推荐结构，用于说明归属关系，不代表要求立即调整现有目录：

```text
根目录/                         # ROOT
├── AGENTS.md
├── <工作区>/                   # WORKSPACE
│   ├── AGENTS.md
│   ├── index.yaml              # 当前工作区的项目与仓库资源映射
│   ├── repos/                  # REPOS：项目集合
│   │   └── <项目>/             # PROJECT：跨仓库协作边界
│   │       ├── AGENTS.md
│   │       ├── <前端仓库>/
│   │       └── <后端仓库>/
│   ├── change/                 # CHANGE：按项目记录需求与设计
│   │   └── <project-id>/
│   ├── wiki/                   # WIKI：可选，按项目/仓库构建知识图谱
│   │   └── <project-id>/
│   └── knowledge -> ../knowledge/workspaces/<工作区>   # 软链接，工作区通用知识入口
└── knowledge/                  # KNOWLEDGE：人工知识集中管理目录
    ├── workspaces/             # 工作区级 KNOWLEDGE 的实体目录
    │   └── <工作区>/
    └── <其他知识目录>/         # 根目录级 KNOWLEDGE
```

`WORKSPACE` 使用与其 `AGENTS.md` 同级的 `index.yaml` 维护索引，不设置独立的 `index/` 目录或 `INDEX` 目录类型。基本目录为 `repos`、`change`；`wiki` 和 `knowledge` 可选，不要求预先创建。`wiki` 与项目、仓库绑定，通过 `index.yaml` 映射；`knowledge` 不绑定具体项目或仓库，不纳入 `index.yaml`，实体集中存放在根目录 `knowledge/workspaces/<工作区>/`，工作区内仅保留指向它的软链接，并在工作区 `AGENTS.md` 中登记。`change` 和可选的 `wiki` 推荐放在工作区对应目录下并按项目分组，通过下述映射关联项目和代码仓库。需求、设计及 AI 工作过程记录必须保存在代码仓库之外，不能因项目目录与仓库目录重合而写入仓库。

## 目录职责与访问权限

| 类型 | 职责 | AI 读取与查询 | AI 写入与维护 |
| --- | --- | --- | --- |
| ROOT | 根目录规则、工作区入口及独立知识目录入口 | 当前任务所需的根目录信息 | 仅处理明确的根目录任务，不批量进入工作区 |
| WORKSPACE | 隔离的工作区，容纳相关项目及共享资源 | 当前工作区内与任务相关的资源 | 当前任务涉及的资源，遵守项目边界 |
| PROJECT | 一个项目及其相关仓库的协作边界 | 同一工作区内可查询 | 可按任务需要联动修改本项目的多个仓库 |
| REPOS | 代码仓库或项目集合的容器 | 同一工作区内可查询 | 按所属项目和仓库规则操作，不因共享容器扩大修改范围 |
| REPO | 单个代码仓库及其构建、测试、版本控制等约定 | 当前任务涉及且所属工作区允许查询的内容 | 仅修改当前任务涉及的仓库，不因仓库级规则扩大项目或跨仓库权限 |
| CHANGE | 对应项目的需求变更、设计、SDD、代码审查及实施记录 | AI 可读取，并用于理解任务背景 | AI 按任务需要记录到映射目录，不擅自改变需求和验收条件 |
| WIKI | 可选，与项目、仓库绑定的知识图谱 | 存在时 AI 可读取 | AI 发现有价值的信息时推荐记录，按用户要求或已有知识维护约定落实 |
| KNOWLEDGE | 人工整理、独立管理的通用知识，不绑定具体项目或仓库；可位于根目录或工作区 | 不纳入默认搜索；用户明确指定范围后才可读取 | 默认不写入；仅在用户明确要求编辑指定内容时操作 |

### PROJECT、REPOS 与 REPO

1. `repos/` 是容器，不是跨项目修改授权。分组仓库的关系为 `WORKSPACE → REPOS → PROJECT → 代码仓库`；未按项目分组的仓库可直接位于 `repos/` 下，在索引中归入特殊分组 `_`。
2. 同一 `PROJECT` 内的仓库可以互操作；与该 `PROJECT` 同级的其他项目不属于同一个协作边界。`_` 只是未分组仓库的索引容器，不是实际项目，不授予其中仓库之间的跨仓库修改权限。
3. 每个仓库仍保留自己的构建、测试、版本控制和提交约定。跨仓库修改须分别验证，并清楚列出各仓库的变化；不得自动合并其提交或发布流程。

### index.yaml：项目与仓库的资源映射

1. 每个工作区只有一个工作区级 `index.yaml`，与该工作区的 `AGENTS.md` 同级，由 AI 自行维护。它是项目、仓库及对应 change/wiki 目录映射的唯一维护入口；项目和仓库的 `AGENTS.md` 负责行为约定，不再重复维护路径映射表。
2. 顶层字段为 `project`，其值必须是列表。每项使用 `name` 和 `repos`；仓库条目使用 `name`、`path`、`change`、`wiki`。不得通过重复 YAML 键表示多个项目，以免解析时覆盖。
3. 项目名在工作区内唯一，仓库名在所属分组内唯一，仓库 `path` 在工作区索引内唯一。`_` 是保留分组名，专门表示未按 PROJECT 管理的仓库，不要求建立名为 `_` 的目录。
4. 所有路径相对于所属 WORKSPACE 根目录解析，不相对于终端目录、代码仓库或其他声明文件。路径必须留在当前工作区内，不得通过绝对路径、`..` 或符号链接绕过隔离。路径采用规范化相对形式；进行唯一性、包含关系和越界判断前，须消除 `./`、重复分隔符和末尾分隔符等等价写法，并核对已有路径及符号链接的实际解析位置。规范化后的仓库 `path` 不得互相包含；当前索引不支持同时登记具有包含关系的嵌套仓库或 submodule，遇到这种结构时先请用户明确登记范围。
5. `path` 指向实际存在的代码仓库；`change` 指向该仓库的需求、设计及审查记录目录；`wiki` 指向可选的知识库目录，没有已确定的目标时使用 `null`。change/wiki 目标必须位于所有已登记仓库的 `path` 之外，不只是当前仓库之外。
6. 推荐分组仓库使用 `change/<项目名>/<仓库名>`、`wiki/<项目名>/<仓库名>`；未分组仓库使用 `change/<仓库名>`、`wiki/<仓库名>`。已有目录以核实后的映射为准，不为统一结构迁移内容；多个仓库可明确映射到同一项目共享目录。
7. 映射中的 change/wiki 路径可以是已明确约定的待创建目录，不代表目录或内容已经存在。有变更记录需要时再创建 change 目标；wiki 按可选知识维护规则处理，不因索引条目自动创建。
8. 项目或仓库的 `AGENTS.md` 如需保留定位标识，只记录 `project_name`、`repo_name`，并指向所属工作区的 `index.yaml`。变更记录中的 `project_id`、`repo_id` 分别对应索引中的项目名、仓库名。项目名和仓库名作为关联标识应保持稳定；确需重命名时，须在对应 change 目录留下旧名、新名和原因等迁移说明，并核对索引与相关引用，不得无说明地改写历史记录。
9. 从仓库查询时，先确定所属工作区，按相对仓库路径匹配索引条目的 `path`，再读取对应 change/wiki。重名仓库不能仅按 `name` 匹配；尚未收录时，只在当前工作区内核实并补充条目。
10. 索引只保存资源定位信息，不存放源代码、需求正文或审查报告。实际内容和目录状态须核对源文件，不把尚未创建的目录或未经验证的条目视为已存在资源。

格式示例（仅说明结构，不代表这些仓库均存在于当前工作区）：

```yaml
project:
  - name: _
    repos:
      - name: standalone-repo
        path: repos/standalone-repo
        change: change/standalone-repo
        wiki: null
  - name: backbone
    repos:
      - name: backbone-java
        path: repos/backbone/backbone-java
        change: change/backbone/backbone-java
        wiki: wiki/backbone/backbone-java
      - name: backbone-javatest
        path: repos/backbone/backbone-javatest
        change: change/backbone/backbone-javatest
        wiki: wiki/backbone/backbone-javatest
```

没有已登记仓库时使用 `project: []`，不将示例仓库写入实际索引。索引允许按任务增量补全，空列表或未收录不代表工作区没有仓库。

### 索引维护

1. AI 发现新仓库、仓库移动或 change/wiki 映射变化时，自行更新当前工作区的 `index.yaml`，无需用户逐次要求。保留无关条目，路径未知时先核实，不编造关联。
2. 缺少索引时围绕当前任务建立必要条目，不默认遍历整个工作区；用户要求初始化或全面核对时，限定在指定工作区逐一处理。
3. 更新后检查 YAML 语法和重复键（解析时不得静默覆盖重复键）、名称及规范化路径唯一性、仓库路径是否存在和是否重叠、映射是否越界，以及 change/wiki 是否位于所有已登记仓库之外。不得因目标目录尚未创建就认定约定的 change/wiki 路径无效。
4. 无法核实时说明涉及的条目和原因，不把未验证映射当作确定事实。不收录其他工作区或未经授权的 KNOWLEDGE 内容。
5. 从旧 `index/` 迁移须属于用户明确的迁移任务。先检查并保留实际索引内容，将维护约定并入工作区 `AGENTS.md`；完成并核对迁移后，仅可清理已确认无用途的旧说明文件和空目录。不得仅凭目录为空或推断无用途进行删除，不删除未迁移资料。

### CHANGE

1. `change/` 按对应项目记录需求变更、方案设计、决策、验收条件及实施结果，回答“为什么改、改什么、如何验收、实施到哪一步”。每项变更应有稳定的 `change_id`，注明 `project_id` 和涉及的 `repo_id`，便于索引关联。一项变更只维护一份主记录。
2. AI 对话中需要保留的 SDD、需求分析、设计方案、实施计划、任务清单、代码审查（code review）发现与处理结果，在单仓库变更中统一记录到 `index.yaml` 对应仓库的 `change` 目录下，可按 `<change_id>/` 分组。不得将这些过程文档、对话转录或审查报告写入代码仓库，包括仓库的 `docs/`、隐藏目录或临时文件。
3. 跨仓库变更写入所属 `PROJECT` 的项目共享 `change` 目录，相关仓库应在 `index.yaml` 中共同映射该目录。尚未共同映射时，先核实已有目录，在任务范围内明确共享目录并更新相关映射，同时留下旧位置与新位置的迁移说明，确保既有记录仍可定位；不得自动迁移历史记录。主记录须列出全部 `repo_id` 和各仓库实施结果，不得在各仓库目录复制多份主记录。`_` 不是项目，不适用项目共享目录规则。
4. 只沉淀与项目变更相关且有保留价值的信息，不机械保存全部对话。区分已确认内容、待确认事项和实施结果，历史记录不得被无说明地改写，旧记录不自动覆盖用户当前明确要求。
5. 代码仓库内仍可按任务维护产品本身所需的正式文档，例如 README、接口说明和使用指南；不得将 AI 过程记录改名后作为正式文档写入。

### WIKI

1. `wiki/` 按项目、仓库构建知识图谱，内容须能归属到 `index.yaml` 中的具体项目或仓库；与项目无关的通用知识不写入 `wiki/`。`wiki/` 不是必需目录，缺失不阻塞开发、查询或索引维护，也不要求每次任务结束后创建知识文档。
2. AI 发现值得复用的知识，例如稳定的业务概念、架构决策、排障经验或操作说明时，可推荐记录到对应项目的 `wiki`，说明建议内容及价值；按用户要求或已有知识维护约定落实写入。
3. 记录时应注明项目归属、来源路径及适用范围，区分已核实事实与推测。临时方案和未确认结论不直接写成既定知识。
4. 建立知识库或调整路径后，更新工作区 `index.yaml` 对应条目的 `wiki`。已发现的过期内容应提示修正，不把知识库维护扩展成无关的批量改写。

### KNOWLEDGE

1. `KNOWLEDGE` 用于人工沉淀通用知识，例如技术规范、领域概念、方法论和跨项目经验，不绑定具体项目或仓库；`wiki/` 则是 AI 维护的项目级知识图谱。两者互不替代，`KNOWLEDGE` 不作为工作区共享资源默认开放。
2. 所有 `KNOWLEDGE` 集中管理在根目录 `knowledge/` 下。工作区级知识的实体目录为 `knowledge/workspaces/<工作区目录名>/`，仅服务于同名工作区；`knowledge/` 下的其他内容为根目录级知识。两者均不在 `index.yaml` 中映射。
3. 创建工作区级 `KNOWLEDGE` 时，先在 `knowledge/workspaces/` 下建立与工作区目录同名的实体目录，再在该工作区根目录创建相对软链接 `knowledge -> ../knowledge/workspaces/<工作区目录名>`，并在工作区 `AGENTS.md` 中登记 `knowledge/`。工作区内已存在同名真实目录时，仅在其为空时替换为软链接；非空时先询问用户，不自动迁移或合并内容。
4. 该软链接是根目录内的受控例外，只能指向本工作区对应的实体目录。不得通过它或 `knowledge/workspaces/` 访问其他工作区的知识；根目录级知识不链接到工作区。
5. 无论其实际位置在根目录还是工作区内部，都保留独立访问规则。不得自动扫描、索引、迁移、同步或改写其中内容。
6. 用户指定访问时，仅处理指定内容；该授权不解除根目录边界和工作区之间的隔离。
7. 工作区内部的 `KNOWLEDGE` 应在所属 `WORKSPACE` 的 `AGENTS.md` 中以相对路径登记。工作区搜索前按登记路径排除，不通过递归扫描发现；已知存在但未登记或归属不明确时，先询问用户，不读取或写入其内容。根目录级 `KNOWLEDGE` 仍须由用户明确指定路径和范围后访问。

## AI 执行顺序

1. **确定范围**：确认任务属于根目录还是某一个工作区；涉及代码修改时，进一步确定项目和仓库。
2. **加载约定**：读取目标路径上适用的 `AGENTS.md`，确定允许查询和修改的范围。
3. **定位资源**：优先利用所属工作区的 `index.yaml`、项目文档或明确路径，再在允许范围内定向搜索。禁止从根目录递归搜索所有工作区；工作区内搜索须按所属 `WORKSPACE` 的 `AGENTS.md` 登记路径排除独立的 `KNOWLEDGE` 目录。
4. **核实并执行**：核对源文件、相关需求和当前状态，在任务范围内修改并按项目约定验证。工具的搜索路径、输出路径和链接目标也须符合访问边界。
5. **同步并报告**：将需要保留的需求、设计和审查记录按 `CHANGE` 规则写入对应的 `change/`，自行更新受影响的 `index.yaml` 条目；发现值得沉淀的知识时推荐记录到可选的 `wiki/`。说明修改范围、验证结果及未完成事项，不宣称未执行的检查已经通过。
