# .docs、change 与 wiki 规则

## .docs 访问入口

Agent 通常在仓库目录内工作，工作区级 `change/`、`wiki/` 在其外，访问会触发跨目录权限。`<仓库>/.docs/` 让这些目录出现在仓库路径内，读写都落到实体目录。

1. `.docs/change`、`.docs/wiki` 是符号链接，分别指向 `index.yaml` 中该仓库的 change/wiki 目标。`.docs/` 内只允许这两个链接，不存真实文件或目录。
2. 链接目标只由 `index.yaml` 计算，`.docs` 不能反过来作为映射依据。使用相对路径，目标必须解析到当前工作区内该仓库登记的目录。不得指向其他项目、其他工作区、`KNOWLEDGE` 或根目录外。
3. 跨仓库变更中，相关仓库的链接指向同一个项目共享目录，主记录仍只有一份。
4. 目标缺失时先创建目录再建链接，不留悬空链接。`wiki` 为 `null` 时不建链接，除非当前任务需要写入 wiki。新 clone、新 worktree 或链接缺失、失效时，只补建当前任务涉及的仓库，不批量遍历。已存在同名真实文件或目录时不覆盖，先问用户。以上由 `ws.py sync-docs` 完成。
5. `.docs/` 已由用户的全局 gitignore 排除。不修改全局 gitignore，不暂存或提交 `.docs`。若它出现在 `git status` 中，提示用户，不自行改仓库的 ignore 配置。
6. 部分工具默认不跟随符号链接：在 `.docs` 中查找时显式指定 `.docs/change` 或 `.docs/wiki`；对源码的常规搜索排除 `.docs`，避免把过程记录当作源码。
7. 登记、移动、重命名仓库或变更映射后，运行 `ws.py check` 核对链接目标存在、解析结果位于本工作区且与索引一致。
8. `.docs` 只是让访问路径位于工作目录内。若工具按真实路径判断权限仍提示授权，按提示处理，不绕过。

## CHANGE

1. `change/` 记录需求变更、方案设计、决策、验收条件和实施结果，回答为什么改、改什么、如何验收、实施到哪一步。每项变更有稳定的 `change_id`，注明 `project_id` 和涉及的 `repo_id`。一项变更只维护一份主记录。
2. 需要保留的 SDD、需求分析、设计方案、实施计划、任务清单、审查发现与处理结果，单仓库变更记录到该仓库的 change 目录，可按 `<change_id>/` 分组。
3. 跨仓库变更写入所属 `PROJECT` 的项目共享 change 目录，相关仓库在 `index.yaml` 中共同映射它。尚未共同映射时，先核实已有目录，在任务范围内确定共享目录并更新映射，同时留下旧位置与新位置的迁移说明，不自动迁移历史记录。主记录列出全部 `repo_id` 与各仓库实施结果，不在各仓库复制多份。`_` 不是项目，不适用共享目录。
4. 只沉淀与变更相关且有保留价值的信息，不机械保存对话。区分已确认内容、待确认事项和实施结果。历史记录不得被无说明地改写，也不擅自改变需求和验收条件。
5. 不得把 AI 过程记录改名后当作正式文档放进仓库。

## WIKI

1. `wiki/` 是 AI 维护的项目级知识，内容须能归属到索引中的具体项目或仓库。与项目无关的通用知识不写入 wiki。wiki 不是必需目录，缺失不阻塞开发，也不要求每次任务后写文档。
2. 发现值得复用的知识（稳定的业务概念、架构决策、排障经验、操作说明）时，建议记录到对应 wiki 并说明内容与价值；按用户要求或已有维护约定落实。
3. 记录时注明项目归属、来源路径和适用范围，区分已核实事实与推测。临时方案和未确认结论不写成既定知识。
4. 建立或调整 wiki 路径后更新 `index.yaml` 的 `wiki`。发现过期内容提示修正，不扩展成无关的批量改写。
